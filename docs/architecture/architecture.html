1Executive summary

Netra is a working prototype of a centralised video-intelligence platform. Cameras of different types and vendors are onboarded into one registry, monitored continuously, viewed through one console, enriched with AI inference results, correlated against a watchlist and turned into real-time alerts that an operator can act on — including the vehicle's movement history on a map.

Design principles

PrincipleHow it shows up in the architecture
Adapters, not special casesRTSP, ONVIF, HLS, vendor REST APIs and dashcams implement one interface (prepare · probe · playback · teardown). Adding a vendor SDK is one class; nothing else changes.
Move metadata, not pixelsAnalytics run at the edge and send ~0.6 KB events; video is pulled through a gateway only when someone watches it. This is what makes 80,000 cameras affordable.
Stateless, horizontally scalable APIReal-time fan-out goes through Redis Pub/Sub, so any API replica can serve any WebSocket; background work (health probing) is leader-elected so it does not multiply with replicas.
Exactly-once semantics where it mattersIdempotency keys, a temporal de-duplication window and alert cool-down stop retries, repeated ANPR reads and alert storms from creating duplicate records or operator noise.
Secure by defaultEvery request authenticated; camera credentials encrypted and never sent to browsers; video access through short-lived, camera-scoped tokens; SSRF guard; strict CSP; services bound to localhost unless deliberately exposed; everything audited.
Operable for months unattendedHealth checks, restart policies, memory limits, bounded logs, data retention, nightly backups and automatic certificate renewal are part of the design, not an afterthought.

8Watchlist correlation & alerting

Matching

  • Normalisation: upper-case, strip spaces and punctuation (GJ 01 XX 0001 = GJ01XX0001).
  • Exact: dictionary lookup per entity type (vehicle / person).
  • Fuzzy (vehicles, ≥ 6 characters): SymSpell deletion index finds every entry within edit distance 1 in O(length), independent of watchlist size — covers OCR confusions such as 0↔O, 8↔B, a dropped character.
  • Fuzzy matches are raised one severity lower and labelled possible match.
  • Expired (valid_until) and inactive entries never match; changes propagate to all replicas via a Redis version counter.

Alert life-cycle

Storm control — "prevent duplicate or uncontrolled event generation" (brief §9)

LayerMechanismEffect
Transport retriesUnique event_uidA retried request or re-delivered stream message never creates a second row
Sensor repeatsRedis SET NX EX per camera + type + identity (60 s)Many reads of one passing vehicle → one event with a repeat count
Alert stormsOpen alert for the same entity at the same camera within 5 min is updated (hit_count)One actionable alert instead of dozens
Low-quality readsMinimum confidence 0.60; fuzzy matches downgradedFewer false positives reach operators
Abusive producersPer-API-key rate limit (6,000 / min) and 2 MB body limitNo single source can flood the platform

What the operator sees

A toast with sound (triple beep for CRITICAL) and a pulsing map marker appear instantly. The alert view shows the watchlist record (description, make, colour, case reference, agency), the detection in plain language (plate read, confidence, time, camera, address, vehicle seen, number of reads, where the plate was in the frame), warnings for colour mismatch or non-standard plate formats, the camera's live feed, a 40-second recorded evidence clip around the moment of detection, and a response map with the operator's own location, the wanted vehicle's latest sighting, distance and estimated drive time, with a one-click route.

Movement tracing

The trace endpoint returns the most recent 2,000 sightings of an identity in chronological order with leg distance (haversine), elapsed time and implied speed. Two sightings more than 1 km apart at an implied speed above 160 km/h are flagged as impossible travel — possible cloned or duplicate plate. The brief's example (GJ01XX0001 at 10:02 → 10:18 → 10:41) is reproduced by make scenario and shown as a numbered route on the map.

Data conventions

  • All timestamps stored as UTC DATETIME(6) and returned timezone-aware; enums stored as strings for portable migrations.
  • Events keep a location snapshot so history stays correct when a camera is moved (and is exact for moving dashcams).
  • Watchlist entries are deactivated, never deleted, so past alerts remain explainable; audit logs are never pruned.
  • Schema is portable to Amazon RDS / Aurora MySQL without changes; at scale detection_events is partitioned by month.

12Security architecture

Defence in depth: each layer assumes the one in front of it may fail.

Figure 7 — Security layers
Brief §13 requirementImplementation
Authentication & RBACJWT (HS256, 8 h, required exp/sub/typ, unique jti); roles ADMIN / OPERATOR / VIEWER enforced per route; tokens of one type (stream vs access) rejected elsewhere; logout and password change revoke tokens server-side; 5 failed logins lock an account for 15 minutes.
Input validation & secure APIPydantic schemas with length limits on every field, per-protocol URL schemes, coordinates, timestamps with timezone, payload size; semantic checks (camera enabled, skew, age); non-nullable fields protected on update.
Stream URLs & credentialsCredentials encrypted at rest and never serialised; inline credentials rejected; gateway injects them server-side; browsers receive camera-scoped 5-minute tokens verified by the gateway for live, WebRTC and recorded access.
HTTPS / TLSCaddy terminates TLS with automatic Let's Encrypt certificates in production; one-year HSTS in production.
Audit logsLogins (success, failure, lockout), logout, onboarding, field-level edits with secrets masked, status changes, stream and recording access, alert handling, watchlist and API-key changes, password resets.
Rate limitingRedis fixed windows: login per IP, API per user (600 / min), ingest per API key (6,000 / min).
No secrets in Git.env is git-ignored and generated with random values; staged files are scanned against real secret values before commit.
Environment configurationAll settings via environment variables (pydantic-settings); the backend refuses to start in production with a default JWT secret.
Supply chainPinned dependencies; pip-audit and npm audit report 0 known vulnerabilities; CI builds every image.

Verification: 38 automated tests include lockout, server-side logout, forged and wrong-type tokens, seven SSRF payloads (Redis, MySQL, localhost, IPv6 loopback, cloud metadata), scope validation and security headers; live checks confirmed that requests without, or with another camera's, stream token are refused and that internal endpoints are unreachable through the proxy.

14Scalability to 80,000 cameras

80,000 cameras × 2 Mbps ≈ 160 Gbps if everything were sent centrally. The design instead keeps video near the camera and moves metadata: an ANPR event is ~0.6 KB, so 4,000 events/s is only ~20 Mbps into the central tier.

Known limitations of the prototype

  • AI inference and camera feeds are simulated (the brief does not require model training); real models post to the same API.
  • ONVIF discovery probes configured hosts rather than WS-Discovery multicast, which does not cross container networks.
  • Recording is a 6-hour hot tier; warm and cold tiers are designed (section 14) but not implemented.
  • Department-scoped data access is modelled (departments on users and cameras) but not yet enforced per query.
